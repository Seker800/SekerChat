日期：2026-10-23。以下保留 v0.9.21 发布前的历史验收记录。后续生产验收发现渐进式 JPEG 内存问题，已回滚 v0.9.19；v0.9.21 未获生产验收通过，不得再次部署。修复后实际发布并验收的是 v0.9.22，见[生产发布记录](./production-release-v0.9.22.md)。

相对 v0.9.19，此次主要包含 QQ 附件、上传进度/恢复/取消、文件引用一致性与安全边界、持久化图片预览任务、桥接空轮询与心跳优化、长历史虚拟列表及工程门禁修复。

## 生产快照的本机演练

生产只执行逻辑备份、运行镜像及少量对象样本的单向导出。所有恢复、迁移、测试写入与回滚均在本机临时容器内完成，不使用生产数据库或 bucket 作为开发连接。

验收完成后，已删除本次四个临时容器、两个网络及测试专用旧镜像标签。最终候选产物和受限权限的本机备份/验收证据保留。最后只读复核确认生产前后端仍为原有 v0.9.19 镜像、健康正常，后端就绪检查返回 200。

恢复的基线含 49 张表、17 个用户、5,343 条消息、2,225 个文件记录。迁移历史中有 112 个成功迁移，与仓库一致；仅以下两条待执行：

1. `20261023010000_file_preview_jobs`：新增任务表、约束、索引及历史图片任务意图。
2. `20261023011000_file_preview_job_utc`：将新表的默认时间及待处理任务时间统一为 UTC。

演练结果：

- 旧版实际运行镜像保持服务时执行两条迁移成功；包括校验的演练阶段约 13.9 秒，不是 NAS 执行耗时预测。
- 所有原有业务表行数一致；User、Group、Message、FileObject 的行级指纹一致，索引和约束有效。
- 生成 1,539 个 READY、176 个 PENDING 预览任务；未删除旧结构或重写核心业务行。
- 迁移后旧 v0.9.19 后端仍就绪；最终 v0.9.21 镜像重复执行 migration deploy 返回无待迁移项。
- 启动新版后，登录、群组读取、消息幂等、分片查询/取消、完成上传幂等、非成员拒绝访问均通过。
- 新版实际上传 54,511,172 字节、6,800 × 11,027 像素 PNG，两个分片；缩略图生成及原图内容校验通过。
- 从生产导出的 3 组附件原图与缩略图在本机读取并通过 SHA-256 校验。
- 使用真实构建镜像的浏览器验收通过，已查看工作区与原图截图；点击前未下载原图，显式打开后原图解码成功。
- Cookie WebSocket 消息推送与重连通过。验收工具现已显式传递配置的浏览器 Origin，遵守生产 CSRF 检查。
- 切回 NAS 实际 v0.9.19 镜像后，登录、群组、样本附件，以及新版创建的图片消息和原图均可读取；随后再次升级到 v0.9.21 也通过相同读取检查。

后端、数据库与对象存储只加入 Docker internal 网络；仅前端额外连接本机回环发布端口所需的入口网络。使用独立测试凭据，恢复副本中的桥接连接和 bot 配置已在本机停用。对象存储只恢复样本，因此迁移一致性检查后，将未导出的历史对象任务在本机标为失败以隔离测试队列；没有对生产任务做此操作。

回滚镜像由 NAS 当前运行镜像导出。Docker 的不同镜像存储可能产生不同的本地 image ID；已比较所有文件系统层、平台，以及 Env/Cmd/Entrypoint/WorkingDir/User，确认本机导入镜像与生产导出相同。演练是应用级回滚，不执行数据库 down migration。

## 产物与后续发布顺序

本机 `APP/.deploy-artifacts/` 中已生成：

- `sekerchat-{frontend,backend}-v0.9.21.tar.gz`
- `sekerchat-{frontend,backend}-v0.9.21-sbom.spdx.json`
- `sekerchat-v0.9.21-deploy-config.tar.gz`
- `sekerchat-v0.9.21.release.env`
- `sekerchat-v0.9.21.preflight.json`
- `sekerchat-v0.9.21.sha256`

配置包仅含 app-only Compose、release/rollback/backup/compose 校验及内存观察脚本；不含 `.env`、maintenance Compose、数据库或对象数据。NAS 上五个发布/回滚脚本的 checksum 已与仓库核对一致；app-only Compose 的待更新内容是应用与迁移容器的日志轮转。

在用户另行明确授权部署生产后，按 [唯一发布手册](./synology-deployment.md) 执行：

1. 复核当时生产版本、健康和回滚镜像；保存旧 app-only Compose，更新配置包中的应用 Compose，保留生产私有配置及数据面。
2. 上传上述候选产物，校验 SHA-256 后加载两个镜像。读取 preflight manifest 中的 config digest，区分 Docker 存储的本地 manifest ID 与 NAS 经典 image ID，核对载入的实际镜像。
3. 使用显式 `APP_IMAGE_TAG=v0.9.21` 运行 `release.sh`。脚本必须成功完成新的数据库备份、schema validate 和独立迁移，才替换 backend/frontend。
4. 从用户真实外网入口验证登录、消息、上传/缩略图/原图、切群、QQ 同步及 WebSocket 重连。NAS 监听端口与路由器映射端口分别核对。
5. 失败则使用明确的 `APP_ROLLBACK_TAG=v0.9.19` 执行应用回滚；保留新增任务表，不自动恢复数据库或删除对象。
6. 验证成功后再持久确认生产配置的版本指向，并在镜像构建源提交 `dca6ea8` 上创建正式 annotated tag `v0.9.21`。本次未提前打 tag。

## 观察范围

本机按生产限制运行 backend 512 MiB、frontend 128 MiB。约三分钟的 18 次采样中，观察到的最高占用分别为 216.6 MiB、35.68 MiB，没有 OOM 或进程退出；这是短时本机证据，不能替代 NAS 上的长期观察。

上线后重点观察 176 个历史待补图任务带来的临时 CPU/磁盘负载、缩略图失败与重试、写接口与桥接请求的同窗口延迟，以及长历史输入/滚动和四小时以上的内存趋势。硬件 WAL 落盘瓶颈没有通过本次应用修复消除。

本次只完成数据库快照与对象样本的恢复，不将其描述为全量 PostgreSQL/MinIO 配对灾备演练；对象备份的独立存储与完整恢复验收仍遵循运维手册的单独维护流程。
