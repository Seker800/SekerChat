## 首次尝试与修复依据

v0.9.21 启动健康，但历史预览回填期间发生一次后端 OOM，立即通过已有应用回滚脚本恢复 v0.9.19，未回退数据或修改对象引用。没有将这次尝试认定为上线成功。

当时正在处理的私有历史 JPEG 约 13 MiB，实际为 15000 × 6291（约 94 MP）的渐进式图像。单向导出至本机后，单次原生解码约需 550 MiB；默认 libvips 操作缓存还会保留已完成解码数据。生产原有 512 MiB RAM 配额不足；在在线后端中额外运行 Node/Prisma 验收进程也放大了同一配额内的压力，不能把它排除为共同因素。

此前预检虽覆盖约 75 MP PNG，只复制了少量历史对象，并将未复制对象的本地回填任务标记失败，未覆盖真实历史渐进式 JPEG 回填负载。这是预检缺口。

修复复用现有共享图像工厂与串行队列：关闭操作缓存、运行镜像设置 `MALLOC_ARENA_MAX=2`，生产后端配额调整为 1 GiB RAM / 1536 MiB RAM 与 swap 合计。图像格式、原图上传成功语义和持久化重试状态未改变。监控报告改为按采样中的真实容器限额判断余量。

依据：[sharp 缓存接口](https://sharp.pixelplumbing.com/api-utility/#cache)、[sharp Linux 分配器说明](https://sharp.pixelplumbing.com/install/#linux-memory-allocator)、[libvips 渐进式图片内存说明](https://www.libvips.org/API/current/developer-checklist.html)。该修复覆盖已验证负载，并非任意尺寸图像的内存保证；更大规模的图片处理需要单独评估工作进程隔离。

## 应用回滚

保留 v0.9.19 镜像，必要时在群晖应用目录执行：

```bash
APP_ROLLBACK_TAG=v0.9.19 SEKERCHAT_COMPOSE_BIN=/usr/local/bin/docker-compose bash ./rollback-app.sh
```

回滚脚本验证前后端恢复，不操作数据服务或执行迁移。成功回滚后应同步将生产 `.env` 的 `APP_IMAGE_TAG` 持久化为 v0.9.19；无需反向迁移或覆盖数据库。回滚至旧应用时新增预览任务表与已生成缩略图可保留。
