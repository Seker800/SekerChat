- 生产部署：`sekerchat-backend:v0.9.31` / `sekerchat-frontend:v0.9.31`，后端启动于 2026-11-26 10:50 UTC（18:50 Asia/Shanghai）
- 采样窗口：部署后约 8 分钟；部署前基线为此前 24 小时日志
- 方式：只读。读取容器日志、`nginx -T`、`docker stats`；未改配置、未写数据库、未重启
- 结论：**网络请求结构和传输字节明显改善；写延迟未变，头像首次加载仍是大图，8 分钟不足以验证长缓存收益**

## 一、已验证的改善

| 指标 | 部署前（24h） | 部署后（约 8 分钟） |
|---|---|---|
| `/workspace/bootstrap` | 260 次，p50 126 ms，nginx 平均 **140 KB** | 2 次，p50 90 ms，平均 **36.5 KB** |
| `/workspace/bootstrap` : `/messages` | 260 : 278 ≈ **0.94 : 1** | 2 : 8 ≈ **0.25 : 1** |
| `/groups` : `/messages` | 1,450 : 278 ≈ **5.2 : 1** | 1 : 8 ≈ **0.13 : 1** |
| `/messages` 响应 | nginx 平均 **18.7 KB** | 200 响应平均 **3.9 KB** |
| `/messages/activity` : `/messages` | 1,432 : 278 ≈ **5.2 : 1** | 8 : 8 = **1 : 1** |
| 重用户 `/groups` 响应 | 最大 **203 KB** | 单次 **27 KB**（gzip 生效） |
| 5xx | — | 0 |
| backend 内存 | 约 221 MB | 约 152 MB |

判断：

- 切频道不再重拉整个工作区；bootstrap 只出现在首次加载/会话恢复，消息只由 `/messages` 负责。
- gzip 已生效：同一个重用户的 `/groups` 从 203 KB 降到 27 KB；bootstrap 从 140 KB 降到 36.5 KB。
- 消息回执裁剪生效：消息页响应从平均 18.7 KB 降到 3.9 KB。
- 活动日历从 60 秒轮询改为事件驱动，活动查询与消息请求的比例从 5.2:1 降到 1:1。
- 部署代码确认包含 `workspace-snapshot`、`group-latest-message`（LATERAL）、头像长缓存和 gzip 配置。

## 二、还不能确认或未改善

1. **写延迟没有变化**：采样窗口内没有用户发消息/上传，无法测到写 p50；代码层只并行了两个 S3 校验，fsync 仍存在。发消息/上传完成预计仍是 400–900 ms，除非把 `pg_wal` 迁到 SSD。
2. **头像首次加载仍是大图**：部署后 4 次头像请求平均 344 KB；存量头像没有回填 256px 版本，新上传才会缩放。长缓存（1 年）需要更长时间才能体现为“重复访问不再下载”。
3. **唯一一次 `/groups` 445 ms**：发生在 18:55:52，和首次 bootstrap、attendance 246 ms、消息 125 ms 同一波，且紧接着大量缩略图/头像加载；后续没有第二次样本。暂按冷启动/同盘 I/O 竞争解释，不能据此判定新查询回归；需要更多样本。
4. **QQ 桥接仍占大头**：8 分钟内 manifest + heartbeat 各 74 次，合计约 148/283 ≈ 52%（24h 基线约 67%–75%），轮询间隔未改。
5. 生产日志中 `ObjectStorageGateway GetObject 304` 警告仍存在（17 次），是缩略图条件请求的既有日志噪声，不是新错误；没有 5xx。

## 三、建议的后续观察

- 连续使用 24 小时后，对比 `/avatars/users/*` 的请求数与 nginx `body_bytes_sent`：预期长缓存让重复访问接近 0；若仍高，需回填存量头像缩放。
- 发一条消息/上传一个文件后，看 `POST /groups/:id/messages`、`POST /uploads/:id/complete` 的 p50/p95；预期软件优化只减少约一次 S3 RTT，fsync 仍在。
- 再取至少 3 次 `/groups` 样本，确认 445 ms 是否复现；若复现，检查当时磁盘 I/O 与 Prisma 查询计划。
